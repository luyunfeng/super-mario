## 当前执行方式（2026-11-17）

以[主线验收矩阵](feature-inventory.md)作为持续目标的完成依据。先映射现有实体和插件，再按独占文件范围并行实施；主线程负责共享契约、兼容、集成与验收。沿用当前分支和工作区，不自行建分支/worktree；已有其他线程改动先保留、核对再集成。下面的早期“不做一键同意/SSH首选/人周估算”不覆盖现有真实实现或当前持续目标。

首批增量为：主 Agent 的执行者/会话态势、机器人可选执行者绑定、受控群聊与事件驱动 A2A。后续继续按矩阵补验收返工、承诺回报、项目跟进、会话发现/恢复、来源采集和决定接续，不将首批当作整个目标结束。健康等非主线能力排除。

## 1. 结论

- 首版目标：用户在 Web 或飞书对主 Agent 说一句话，主 Agent 借助知识选出外部 CLI Agent，在远端机器上执行，结果回到对话。同时，他人发给用户的飞书消息能形成待办。
- 首版不做：以用户身份代发消息、一键同意后自动执行、插件进程隔离、多用户。这些放入二期或以后。
- 拆分方式：先用 2 周定契约（M0），再按 10 个工作包并行开发。每个工作包只通过契约依赖其他工作包；契约负责方在 M0 同时交付假实现（mock），让下游不被阻塞。
- 粗估规模：首版（M0–M6）约 45–58 人周（核心服务和执行机代理比初稿多）。按 5–6 名开发人员计，约 13–15 周。这是无历史数据的粗估，M0 结束后按契约和 spike 结论重估。

### 2.2 首版必须跑通的 3 条主流程

1. **Web 派活**：用户在 Web 对主 Agent 描述目标 → 主 Agent 检索知识、选执行者 → 在远端机器启动 CLI Agent → Web 可看控制台 → 结果回到对话。
2. **飞书派活**：同流程 1，入口和结果回送改为飞书机器人对话。
3. **消息成待办**：他人发给用户的飞书消息 → 识别需处理事项 → 生成或合并待办 → 用户在 Web 查看、修改、关闭，或从待办手动派给主 Agent。

### 5.1 统一状态词表

以下状态分属不同对象，任何工作包不得用一个状态代替另一个：

| 对象 | 状态 | 由谁判定 |
| --- | --- | --- |
| 执行会话 | 存活 / 已断开（客户端） / 已退出 / 不可达 | WP4，依据运行时 |
| 执行尝试 | 排队 / 启动中 / 运行中 / 等待输入 / 等待批准 / 已结束（成功、失败、取消、未知） | WP2，依据适配器上报的原生信号 |
| 待办 | 待处理 / 处理中 / 已完成 / 已忽略 | 首版由用户确认（G8） |
| 二期：批准 | 待批准 / 已批准（绑定版本） / 已拒绝 / 已过期 | WP7 二期 |
| 二期：副作用 | 未发送 / 已发送 / 未知 / 已确认 | WP7 二期 |

“未知”是合法状态。外部调用超时、送达不明时记为未知，不自动重试有副作用的操作。

## 6. 协作规则

1. 每个工作包只依赖契约和假实现，不直接引用其他工作包的内部代码。
2. 契约变更：负责方提出变更说明 → 使用方评审 → 升版本号 → 同步更新假实现。破坏性变更需项目负责人批准。
3. 领域模型（C2）的表结构变更须经 WP0 负责人评审。
4. 每个工作包的“完成”定义：
   - 单元测试和契约测试通过；
   - 契约文档与实现一致；
   - 对应验证用例有执行记录（输入、版本、结果、证据），见 `tests/` 与验收表；
   - 不出现参考项目名称；
   - 已知限制写入工作包说明。
5. 涉及真实飞书账号、真实消息、远端机器安装运行时的测试，执行前须获得用户单独授权。默认使用假 CLI、合成消息和隔离测试账号。
6. 每个工作包开工前阅读第 8 节列出的调研章节。调研结论标为 UNKNOWN 或 NOT-RUN 的事项，不得写成已验证。

### WP0 核心与插件宿主（另含副作用账本、交互卡片、渠道管线、督办与通知）

2026-11-16 插件评审落实：`npm run lint:plugins` 在 CI 同时检查系统插件与第三方风格示例，禁止导入核心内部实现；SDK-only 示例和插件声明扩展点/包装示例均有真实宿主测试。接口与权限以架构第 5、6 节的当前实现说明为准。

- **目标**：提供最小运行核心和插件契约，让其他工作包能以插件方式开发。
- **范围**：
  - 服务端入口、配置加载、日志与 trace ID。
  - 插件清单解析、依赖解析（缺失或循环依赖时拒绝并回滚）、生命周期管理。
  - 资源登记：插件注册的工具、路由、订阅、后台任务在停用时自动释放。
  - 进程内事件总线；关键领域事件落库。
  - SQLite 存储层、迁移机制、每个插件独立命名空间。
  - 单用户认证（登录与会话令牌）。
  - 副作用账本、交互卡片（梯级路由、先答者生效）、可配置的自动处理策略（规则引擎、三层配置、默认审批交给用户，见架构方案 4.12）、渠道管线、督办与通知（巡检、唯一通知出口、可用率记录），见架构方案 4.4、4.5、4.7、4.9。
- **不含**：插件进程隔离、代码热替换、插件分发。停用插件不撤回已发生的外部副作用。
- **依赖**：无（最先开工）。
- **交付物**：C1、C2 文档；`packages/core`、`packages/plugin-sdk`；示例插件；契约测试工具。
- **验收**：P01、P02、P04、P06；示例插件重复启停 100 次后注册计数不变。
- **调研阅读**：`reports/40-plugin-and-super-agent.md` 第 3–5 节；`reports/30-agent-foundation.md` 第 6 节；`reports/72-dispatch-supervision-deep-dive.md`（卡片梯级、督办、通知出口、可用率）。
- **粗估**：6–8 人周（含上面新增的核心服务）。建议两人：一人宿主与存储，一人卡片、账本、督办。

### WP4 执行机代理、终端宿主与终端网关

2026-11-16 完整性验收：执行机单文件制品必须经 Web 查看源码、确认精确版本及 SHA256 后手动加载；未确认、版本或哈希不匹配不 import、不 activate。`tests/agent-artifacts.test.ts` 和 `tests/agent-artifact-transport.test.ts` 覆盖禁止执行副作用及真实 HTTP/WS 确认闭环；不提供自动下载或任意依赖安装。

- **目标**：实现执行机代理和终端宿主，把执行机上的会话安全地接到服务端和浏览器。风险最高的工作包。
- **范围**：
  - 执行机代理 `apps/agent-node`：主动 WebSocket 连接、心跳、重连、配对与机器信任（待确认 → 已信任）、角色；加载插件的执行机一半。
  - 统一会话投影与 `capabilities`；只写自己启动并已绑定的会话；单写者保护与显式恢复。
  - 发送安全：服务端持久去重 + 代理内存去重 + 每会话串行 + 读屏拒绝（对话框、草稿）+ transcript 确认；结果三态。
  - hook 本机 socket；代理断线时 hook 卡片在宽限期内续上。
  - 正文流：带序号订阅、缺口补页。
  - `plugins/terminal-host`：在本机调用终端运行时，版本与能力握手、不兼容时降级或拒绝（T09）；完整定位键防止误控另一台机器（E07）。
  - 终端网关（服务端 ↔ 浏览器）：每条连接独立 epoch/seq；先发 full 再发增量；失步重建基线；背压与缓冲上限（T12）。
  - 控制权：单一控制者 + 多个只读观察者；尺寸由控制者决定（T06）。
  - 断线语义：浏览器断线不关闭执行会话；代理断线重连不重启任务（T03）；运行时或机器重启时显示恢复边界（T07、T08）。
  - 执行机部署说明（安装运行时、CLI、凭证）。实际安装需用户授权。
- **不含**：断线期间完整输出回看（二期评估）；运行时本身的修改。
- **依赖**：C2；S1 结论。
- **交付物**：C4 文档 + 假终端宿主；`apps/agent-node`、`packages/protocol`、`plugins/terminal-host`；终端 WS 协议（C7 的终端部分）。
- **验收**：T01–T12、E07、B03；重连后显示当前画面并继续接收新输出，且不重复启动任务。恢复耗时只测量和记录，指标待用户确定。
- **调研阅读**：`reports/71-remote-takeover-deep-dive.md` 全文；`reports/50-remote-runtime.md` 全文；`reports/10-reference-server-web.md` 第 10 节；综合研究 F09、F11、F12、F15。
- **粗估**：7–9 人周。建议安排两人：一人负责执行机代理与发送安全，一人负责终端宿主与终端网关。

### WP7 收件箱与待办（核心模块 + `inbox-triage` 插件 + `daily-brief` 插件）

- **目标**：把需要处理的消息变成可管理的待办，并与执行尝试关联。规则见架构方案 4.10。
- **范围（首版）**：
  - 收件箱事件：按话题键聚合，同一话题只有一个开放事件；处理链记录每一步及发生位置。
  - 分拣（`inbox-triage`）：三级 `action / fyi / noise`，输出摘要、理由、紧急；模型失败用规则回退，无回退不入库（F06）；同一话题补充时合并（F05）。
  - 静音与策略：发送人 > 聊天 > 来源，由代码执行。
  - 建议：带版本号，首版只有 `todo` 和 `conclusion`；版本不符返回冲突，重复点击无效。
  - 自动归档：来源报告已读/已回时归档并记录依据；重开后同一依据不再归档。
  - 待办：只存事实（截止、提醒、完成、等待对象），分区由服务端统一计算；“等对方”默认 24 小时回看，3 次无进展交还用户；提醒先认领再推送。
  - 人工操作：修改、合并、拆分、忽略、关闭；误判可修正并留痕。
  - 从待办派活：把待办上下文交给主 Agent；执行结束不自动完成待办。
  - 简报（`daily-brief`）：程序算一次事实（今天到期、逾期、等待中、过去 12 小时完成、待处理卡片、打扰次数与可用率），模型只写开头。
- **二期范围**：回复草稿与行动建议（带版本）；批准（绑定版本、范围、期限）；副作用记录（未知状态、不盲目重放）；结果回写。对应 A01–A09。
- **不含**：飞书原生任务同步。
- **依赖**：C2、C5、C6。
- **交付物**：`packages/core` 中的收件箱与待办模块；`plugins/inbox-triage`、`plugins/daily-brief`；分拣提示词与合成测试集。
- **验收**：F04–F06、F09；合成样本的识别结果有记录，误判可人工修正。
- **调研阅读**：`reports/73-inbox-todo-recap-deep-dive.md` 全文；`reports/20-collaboration-knowledge-inbox.md` 第 4–5 节；综合研究 F01、F06。
- **粗估**：首版 4–5 人周；二期 3–4 人周。

### WP8 知识与执行者目录

- **目标**：实现个人、全局、项目三层知识，并为主 Agent 选择执行者提供依据。
- **范围**：
  - 存储：Markdown 文件为事实源；SQLite 索引记录层次、所属项目、来源、版本、更新时间。
  - 检索：首版用全文检索（SQLite FTS），不引入向量库。

## 14. 项目总结

**做什么**：一个只有服务端和 Web 的 AI 工作台。用户只跟一个主 Agent 说话（在 Web 或飞书里），主 Agent 查知识、挑合适的外部 CLI Agent（Claude Code、Codex），派到远端机器上执行，结果回给用户。同时，别人发给用户的飞书消息会自动变成待办。

**首版功能**：主 Agent 对话与异步派活；Claude Code、Codex 两个执行者接入；远端机器连接与可断线重连的 Web 控制台；飞书机器人对话入口；飞书消息形成待办；个人、全局、项目三层知识与执行者自动选择。“一键同意后 AI 代回复或代执行”放二期。

**从参考产品复刻什么**：主 Agent 的派活工具链路；外部 CLI 的启动、原生会话 ID 和 resume 恢复；机器配置与 SSH 连接；终端画面 full/增量帧和浏览器重连协议；飞书机器人渠道与用户授权读消息两条链路；收件箱 → 建议 → 确认 → 待办的结构和“送达未知”状态处理；知识以文件为事实源、数据库做索引。**不复刻**：手机等原生端、多管理节点组网、多种终端宿主、复杂的默认权限体系。从插件宿主参考借鉴依赖声明、生命周期和资源自动释放；从文章和研究原型借鉴“协调者与执行者分层”的思想。

**核心是什么**：三个业务实体（知识、待办、外部 Agent）+ 一个主 Agent。知识让主 Agent 不需要用户说清楚“用谁、在哪、怎么做”，待办承接要处理的事，外部 Agent 负责真正干活。

**架构是什么**：轻核心 + 插件。核心只有插件宿主、领域模型、事件总线、存储和 HTTP/WS 框架；主 Agent 用 pi 的 SDK 同进程实现。工作编排、交互卡片、收件箱与待办的规则在核心；两个 CLI 适配、终端宿主、飞书、分拣、知识、简报是插件，通过扩展点接入（详见架构方案）。远端执行由各执行机上的终端运行时托管；每台执行机装一个执行机代理，主动用 WebSocket 连接服务端，在本机驱动终端和 CLI；服务端再把正文、卡片和终端画面送到浏览器。技术栈建议 TypeScript/Node + SQLite + 本地文件，单用户起步。
