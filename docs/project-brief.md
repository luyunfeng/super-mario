## 目标

建设以 Super Agent 为核心的 AI 工作台。用户通过主 Agent 表达目标，由主 Agent 借助知识发现并选择合适的外部 Agent 和工具，组织执行并反馈结果。首期优先做好飞书连接，同时提供 Codex、Claude Code 等 CLI Agent 的接入能力。具体接口和完整首版范围尚未定稿。

交付形态明确为服务端与 Web，不开发手机端等原生客户端。通过飞书插件使用现有飞书入口，不增加自建手机客户端。

用户认为主要参考项目功能丰富，但结构杂乱、整体偏重。本项目应选择性借鉴功能和实现，保持核心轻量，控制概念、状态和依赖数量。

## 插件设计原则

已确认的产品要求：采用“万物皆插件”的设计理念，把插件体系作为核心设计工作。后续新增能力默认通过插件迭代和补充。基座选择需考虑这一方向，基座的扩展机制与工作台插件的关系尚待核实。

以下是据此提出的设计建议，尚未确定接口或实现方案：

- 保持核心精简，明确核心与插件各自的职责。
- 内置能力和后续扩展尽量使用同一套插件接口，减少特殊路径。
- 插件可独立开发、配置、启用、停用和升级，避免每次扩展都修改核心。
- 优先明确插件接口、生命周期、依赖关系和版本兼容规则。
- 明确插件可访问的能力与数据，并提供错误定位和必要的故障隔离。
- 以首批真实场景验证插件设计，不为假设性需求提前建设复杂插件平台。

外部 Agent 接入、飞书连接及后续飞书智能体相关能力按插件方向设计。工具、技能、模型接入、工作流和界面的具体插件边界，以及插件的分发方式，留待后续确定。当前不承诺兼容任何参考项目的插件协议，也未决定增加第二套插件运行时。

## 首期功能方向

以下为用户已明确的功能方向，尚不等于完整的首版验收清单。

### 外部 Agent 接入

- 默认提供 Codex、Claude Code 等 CLI Agent 的接入能力，其他执行者可通过插件继续补充。
- 主 Agent 能将工作派给外部 Agent，外部 Agent 承担具体执行。
- 用户可以指定执行者，也可以只描述目标，由主 Agent 自己找到合适的执行者和工具。
- 参考主要参考项目中好的接入功能及实现方式；具体通信协议、进程管理和会话恢复方式尚未确定。

### 远端机器与持久终端

用户明确：工作台服务端不一定运行外部 CLI Agent，需要连接运行这些 Agent 的外部机器；默认集成用户指定的终端运行时，并通过插件提供接入能力。

- 支持工作台服务端与 Agent 执行机器分离，不把外部 Agent 限定为服务端本机进程。
- Web 提供对应执行会话的控制台。断线后重新连接，应恢复可查看的终端内容，并继续接收实时输出。
- 在远端运行时和机器正常的条件下，客户端断开不应终止远端执行会话。
- 默认集成是已确认需求，尚未完成安装或接入。通信方式、认证、Web 终端适配和输出恢复速度需要验证。
- 区分网络断线、运行时重启和机器重启。不能把断线恢复解释为原进程能跨机器重启存活。

设计建议：记录“外部 Agent → 执行机器 → 执行会话”的关联，避免将 CLI 类型、实际 Agent 实例和终端位置混为一谈。断线期间可显示明确标记的历史状态，重新连接后核对远端实时状态；不能仅凭断线判定任务失败，也不能根据旧画面判定任务完成。

默认集成的运行时用于托管终端和执行会话，优先选择的 Agent 基座用于主 Agent 的模型与工具执行能力，两者职责不同。具体插件拆分待设计，不为每种 CLI 重复建设整套远端连接机制。

后续建议验收：断开 Web 连接后远端工作继续；恢复连接后重新展示同一会话的控制台并获取新输出，正常执行不重复启动。用户要求尽快恢复显示，但具体延迟指标尚未确定。

### 飞书连接

- 第一期重点做好飞书连接，借鉴主要参考项目的相关能力与实现。
- 飞书连接和飞书智能体相关能力按插件提供，不把具体平台逻辑固化到核心中。
- 首个需要验证的使用流程是：用户在飞书与主 Agent 对话，主 Agent 找到合适的外部 Agent，分派工作，再将结果反馈给用户。此流程是据需求整理的建议，具体入口和交互形式待确认。
- 飞书单聊、群聊、话题、消息卡片、文档或任务等具体覆盖范围尚未明确，不视为全部纳入首版。

### 知识驱动的发现与分派

- 知识体系需要帮助主 Agent 管理和使用外部 Agent。
- 用户不需要把执行者、工具和全部执行细节说明清楚。
- 主 Agent 应依据已掌握的知识补足可推断的执行上下文，发现适合的 Agent 或工具；影响目标、权限或验收的关键未知信息仍需澄清。
- 知识按个人知识、全局知识、项目知识三层组织；更新与检索机制尚未确定，不预先指定知识图谱、向量数据库或其他存储方案。

### 知识分层

用户明确要求区分个人知识、全局知识和项目知识，以同时支持多个工作项目及个人事务。

| 层次 | 作用 | 示例（用于解释，尚非字段设计） |
| --- | --- | --- |
| 个人知识 | 支持个人生活与个人事务 | 个人安排、生活背景、个人事项相关资料 |
| 全局知识 | 指导整体工作方式，跨项目和个人事务适用，是用户特别强调的重要层次 | 工作原则、决策标准、沟通方式 |
| 项目知识 | 支持具体项目，区分多个项目的上下文 | 项目目标、资料、进度、相关执行者 |

全局知识的“全局”指适用范围，不表示对所有用户公开。三层知识的冲突、覆盖、共享及检索规则尚未确定，不能将“更重要”直接解释为无条件覆盖其他层次。

### 飞书消息形成待办

- 用户明确看重从他人发来的飞书消息中形成待办的能力，待办与知识并列为核心功能。
- 飞书连接不仅服务于用户向主 Agent 派活，也需要承接他人发给用户、需要用户处理的消息。
- 消息覆盖范围、读取方式和可获得的权限尚未核实，当前不承诺可以读取用户的全部私聊或群消息。
- 建议识别消息中的处理事项，并关联原消息与上下文。不是每条消息都必须生成待办；识别条件、重复合并和人工调整规则待设计。
- 待办是工作台中的功能与实体，不预设必须使用飞书原生任务，也不预设自动同步到飞书任务。

### 用户同意后由 AI 处理

用户提出的未来目标：对适合交给 AI 的待办，用户一键同意，AI 随后代为回复或完成工作，减少用户手工处理消息和执行事务的负担。

建议的完整流程：飞书消息接入 → 识别处理事项并形成待办 → AI 结合知识提出回复或行动建议 → 用户查看并同意 → 主 Agent 调用合适的工具或外部 Agent → 反馈结果并更新待办。

上述行动建议、结果回写和状态设计是据目标提出的建议。消息形成待办与一键同意执行的分期、首版支持的行动类型尚未确认，不能将用户的未来愿景全部列为首版承诺。

“同意”的具体含义需要在产品设计中明确：用户能看清本次回复内容或拟执行动作，并批准对应范围。单个待办的同意不自动代表长期授权。执行失败应保留真实结果，不能因点击同意就直接标记完成。

## 核心实体与职责

用户当前明确提出的核心实体是“知识”“待办”和“外部 Agent”。以下含义用于需求讨论，不代表数据库模型已确定。

| 概念 | 当前职责理解 | 确认程度 |
| --- | --- | --- |
| 知识 | 分为个人、全局、项目三层，帮助主 Agent 理解背景、遵循工作原则并选择执行者 | 三层划分已明确；具体关系和存储待设计 |
| 待办 | 承接飞书消息等来源中需要处理的事项，未来支持用户同意后交给 AI 回复或执行 | 用户明确提出；状态、行动范围与分期待设计 |
| 外部 Agent | 可接入、可分派工作的执行者，首批包括 Codex、Claude Code | 用户明确提出；注册与运行模型待设计 |
| 主 Agent | 用户的统一对话对象，理解目标并利用知识选择和分派执行者 | 用户明确提出的交互角色 |
| 插件 | 为系统接入和扩展具体能力，首期覆盖飞书和外部 Agent 接入 | 已确认的扩展机制；插件协议待设计 |

外部 Agent 是被管理的执行者，插件是接入和扩展能力的机制，两者不直接等同。知识、待办虽是核心功能，其实现仍遵循插件化方向，不代表必须全部固化进运行核心。项目、工具和执行会话是否需要成为独立实体，后续按真实流程决定。

待办与底层执行任务如何对应尚未确定，不提前建设两套重复的任务模型。

远端运行需求进一步引入“执行机器”和“执行会话”两个基础设施概念：机器承载外部 Agent，执行会话保留终端与运行位置。是否将其独立建模、以及完整生命周期待设计，不将其直接等同于知识或待办等业务实体。

为了支持自动分派，建议知识能关联项目背景、执行者能力、适用范围、工作位置及历史执行经验。上述字段与关系属于设计建议，尚未确认；执行者是否可用等实时状态需核验，不能仅凭历史知识推断。

## 当前任务理解

建设一个以 Super Agent 为核心、通过插件持续扩展的 AI 工作台。插件化是主导架构原则。文章提供自主 Agent 的系统设计方向，主要参考项目提供产品、功能与实现参考，用户选定的基座提供优先考虑的执行底层。

主要参考项目中的好功能及实现可以借鉴。用户对独立命名的要求不应被误解为禁止借鉴或模仿功能。是否复用具体代码尚未确定。

本轮已完成详尽调研和可交接材料。用户已确认要求、上游事实、推断、未知与方案待决项分别记录，让后续 AI 能依据源码和接口证据快速形成方案。本轮没有替用户定案。

新增功能要求进一步明确：以知识和外部 Agent 为核心实体，用户只与主 Agent 对话。主 Agent 应能在用户未指定具体执行者时自主发现并分派，首期重点是飞书连接和 CLI Agent 接入。

后续补充将待办明确为与知识并列的核心功能，并限定交付为服务端与 Web。系统需支持从飞书消息中形成待处理事项，未来实现用户同意后由 AI 回复或执行的流程。完整自动处理范围及分期仍待确认。

文章转载讨论连续交互、并行任务、事件响应与持久运行。它描述的是架构探索，不能把其中全部设想视为参考系统已有能力，也不能直接变成本项目首版承诺。
